2  Public APIs: Our Water Main

Hey analyst! Welcome to Chapter 2 of 🌧️ Raining Tables 🌧️

Hold onto your hats! 🪁 Today, we’re talking about APIs. ⛲

Today we’re hooking up to our NOAA API water main. No more hauling csvs around; we’ll have our data on tap. 🚰

Said differently: instead of re-downloading a csv every update, running our scripts will call NOAA’s API directly and pull their data into our programming environment.

✨ ~ pretty amazing ~ ✨

So how do APIs work?

NoteWhat’s an API?

An API, or Application Programming Interface, is a programmatic way to interact with a webservice.

For our purposes, automating a public data pull, the NOAA API gives us a way to request data using a script, rather than us manually clicking through their website’s user interface. Our API call returns the data we need in an efficient, standardized, and predictable way. 🚰

First, we need to request an API key🔑 , a user password we add to our API call so NOAA recognizes us, like our ID:

  • Go to NOAA’s API page to request a key.
  • Submit the email address you want associated with this project.
  • They’ll send you an email with your API key 🔑, a long string of letters and numbers. Copy this string.
  • Save this string in .Renviron, your environment file (see here for an example), so your script knows where to look for it. Don’t copy-paste it directly in your code! If you copy-paste into your code, you could expose it when sharing code or posting on GitHub. Saving in .Renviron keeps your password a secret. 🤫

Format your .Renviron file as:

NOAA_CDO_KEY=abcde12345

where NOAA_CDO_KEY is an example name you make up for your key and abcde12345 is the API key 🔑 you received from NOAA.

No spaces, no quotes.

Have your API key safely saved in .Renviron? Excellent, let’s start! 🥳

API Calls

Most API calls are a URL that combine your unique API key 🔑 with a collection of other strings, data parameters that identify our specific data cut. These parameters might specify a particular date range, series ID, time frequency, unit of measurement, data flags, or other attributes.

Knowing how to format the call requires reading the data source materials and reviewing their examples. The format’s quite fiddly! If we don’t string the parameters together in the exact order, the API call won’t go through.

Let’s walk through the NOAA call from R/pull_daily_rain. Remember we’re hooking up to our data source water main ⛲: we’ll explore the different pipes, then connect the pipes together and test our taps. 🚰

Our API key

For calling data in a report, we first save our key as an object (api_key) and use nchar() to check it exists without printing it and exposing it:

# Sys.getenv() is how we call our key from the .Renviron environment file 🔑
api_key <- Sys.getenv("NOAA_CDO_KEY")
nchar(api_key) # returns 32 if it's set, 0 if it isn't
#> [1] 32

What we’re asking for

We may want many cuts of data, so R/pull_daily_rain API call should be relatively flexibly and easy to change. For this we set our data parameters as function arguments. Change our arguments lets us retrieve different cuts of data.

To show this concretely, let’s set the parameters for a data cut for zipcode 97205, the beautiful but rainy Portland, Oregon. 🌧️

zipcode <- "97205"
date_start <- "2024-01-01"
date_end <- "2024-12-31"
units <- "standard"
limit <- 1000

location_params <- paste0("&locationid=ZIP:", zipcode) # specifies we're using zipcodes for location
location_params
#> [1] "&locationid=ZIP:97205"

Side note: if you look in R/pull_daily_rain, you’ll see it’s our choice to use zip codes to specify location in location_params. NOAA also gives us the option to specify location using weather station IDs, IDs for the specific sites weather data are collected. Finding weather station IDs takes a bit more digging, though, so we’re using zip codes.

The URL

Next, we string our URL strings together, like fitting pipes. 🔧

# stringing our data cut parameters to NOAA's URL string:

url_string <- paste0(
  "https://www.ncei.noaa.gov/cdo-web/api/v2/data?",
  "datasetid=GHCND",
  "&datatypeid=PRCP",
  location_params,
  "&startdate=", date_start,
  "&enddate=", date_end,
  "&units=", units,
  "&limit=", limit
)

# just keep stringing 🐟

url_string
#> [1] "https://www.ncei.noaa.gov/cdo-web/api/v2/data?datasetid=GHCND&datatypeid=PRCP&locationid=ZIP:97205&startdate=2024-01-01&enddate=2024-12-31&units=standard&limit=1000"

URL formats

Note: the NOAA API’s standard URL string typically won’t change unless NOAA intentionally updates its backend infrastructure. If we’re building a product using NOAA’s API, we should subscribe to NOAA updates or notifications so they can communicate any changes to us.

Reliable public data flows and user communications are hallmarks of working #publicdatainfrastructure. ⛲ 🌉 ⛲ 🚃 ⛲ 🌆

We’ve added all the parameters we need for our data cut! Last step: including your API key. 🔑

ImportantWhere the key goes

In the case of the NOAA API, we’re not adding our API key 🔑 directly into our call URL. NOAA wants it in a request header, which is a bit different (see code below).

Many other APIs expect &api_key=... directly added to url_string. If that’s the case, the full URL itself is a secret: don’t print it, don’t log it, don’t paste it anywhere. 🤫 For other APIs, review their user manual and check their API call format.

Calling our data

response <- httr::RETRY(
  verb = "GET",
  url = url_string,
  httr::add_headers(token = api_key),
  httr::timeout(10),
  times = 3,
  pause_base = 1,
  pause_cap = 10,
  quiet = TRUE
)

response
#> Response [https://www.ncei.noaa.gov/cdo-web/api/v2/data?datasetid=GHCND&datatypeid=PRCP&locationid=ZIP:97205&startdate=2024-01-01&enddate=2024-12-31&units=standard&limit=1000]
#>   Date: 2026-09-29 23:40
#>   Status: 200
#>   Content-Type: application/json
#>   Size: 41.5 kB

RETRY() is GET() with a fail-safe built in:

  • if the first call doesn’t go through, or if the connection times out, it waits and tries again instead of failing.
  • pause_base = 1 and pause_cap = 10 create this recurring call for us.

If we need it, the response output above also contains information about our call status (ie, if it ran successfully) and any associated messages. If our call fails, we can check error or other messages by viewing its status:

httr::status_code(response)
#> [1] 200
httr::http_status(response)
#> $category
#> [1] "Success"
#> 
#> $reason
#> [1] "OK"
#> 
#> $message
#> [1] "Success: (200) OK"
TipSeeing the HTTP request in action

As an experiment, let’s see our call in action by wrapping it in httr::with_verbose():

httr::with_verbose(
  httr::GET(url_string, httr::add_headers(token = "put-a-fake-token-here"))
)

The console output shows us step-by-step what we’re doing when we send this call: our request, a request timestamp, where the data are hosted, the content size and type, and whether the call ran successfully:

-> shows what we sent. <- shows what’s returned.

Why use a fake token? The verbose output prints your headers, including your API key🔑. Remember, if you run it with your real key, you’ll reveal the key in your console history or log. This is also why “here’s my verbose output” is a common way to leak a key. Watch where you put your keys! 🤫

Most APIs return data in a format called JSON as a list of nested values. There are two top-level pieces: metadata, which describes the response, and results, our data.

Under parsed$metadata, we can review parsed$metadata$resultset to ensure we’ve collected all the data we asked for, rather than hitting NOAA’s data limit:

parsed$metadata$resultset
#> $offset
#> [1] 1
#> 
#> $count
#> [1] 359
#> 
#> $limit
#> [1] 1000
Warningcount vs. limit

count shows how many observations NOAA returned from our request, but limit is its observation cap. If count is larger than limit, we didn’t get all our data, just the first page, with no error to warn us.

NOAA’s ceiling is 1000 observations per request, and a year of daily precipitation data for a given zip code can blow past that. The fix is the offset parameter: ask again starting at record 1001, then 2001, until you’ve got count of them.

What if your API call fails?

It’s pretty common for API calls to fail on the first try, especially if you’re requesting a large amount of data or if your connection’s spotty. We can usually resolve this by trying multiple times, like in httr::RETRY(). If your call’s still failing or simply taking a long time, and you’re sure it’s not a bug, consider breaking up your data request into smaller cuts. For example, if you’re having trouble pulling ten years of data, try two calls pulling five years of data.

If at first you don’t succeed, try, try again! 😆

More importantly, how do we know if our call fails? Unless our program flags the fail, it’ll continue running, try to parse the error message, and error out. To prevent this from happening, we need to add checks:

# us calling an API with a nonexistent key
bad <- httr::GET(url_string, httr::add_headers(token = "definitely-not-a-token"))

httr::status_code(bad)
#> [1] 400
httr::stop_for_status(bad, task = "pull data from NOAA CDO API")
#> Error:
#> ! Bad Request (HTTP 400). Failed to pull data from NOAA CDO API.

Despite the bad call, GET() doesn’t throw any errors. 🧐 Counterintuitively, GET() has no reason to flag failed calls unless we tell it to. stop_for_status() is our flag. Without it, our script sails on 🌊 ⛵ 🏔️, tries to parse an error message as data 💥 🏔️, and stalls out. If we don’t add this kind of check, we’ll be wondering why our run failed and have to debug.

The whole function

Everything above, with the printing taken out and the edge cases put in:

Code
R/pull_daily_rain.R
#' Pull daily rain
#'
#' Pull daily precipitation data from the NOAA Climate Data Online (CDO) Web Services API, either
#' for a zip code (using NOAA's own zip-to-station aggregation) or for one
#' or more specific stations (e.g. the output of \code{find_nearby_stations()}).
#'
#' Dependencies: httr, dplyr
#'
#' Request a NOAA CDO Web Services API key here:
#' https://www.ncdc.noaa.gov/cdo-web/token
#'
#' NOAA's API documentation can be found here:
#' https://www.ncdc.noaa.gov/cdo-web/webservices/v2
#'
#' You can search NOAA's data resources using their CDO Search here:
#' https://www.ncei.noaa.gov/cdo-web/search
#'
#' A good explainer of how to search NOAA weather data:
#' https://www.youtube.com/watch?v=YY8JYbEO3Ow
#'
#' @param api_key Character. Your NOAA CDO API key.
#' @param zipcode Character. 5-digit US zip code (keep as character to
#'   preserve leading zeros, e.g. "02138"). Ignored if \code{stationid} is
#'   supplied.
#' @param stationid Character vector, optional. One or more NOAA station IDs
#'   (e.g. "GHCND:US1WAKG0072"), such as the \code{id} column returned by
#'   \code{find_nearby_stations()}. When supplied, data is pulled for these
#'   specific stations instead of the zip code's default station pool.
#' @param date_start Character. Start date, format "YYYY-MM-DD".
#' @param date_end Character. End date, format "YYYY-MM-DD". NOAA CDO API
#'   requires date ranges of one year or less per request for GHCND.
#' @param units Character. "standard" or "metric". Defaults to "standard".
#' @param limit Integer. Max records per request (NOAA's ceiling is 1000).
#'   Defaults to 1000.
#'
#' @return A data frame of daily precipitation (PRCP) records, or an empty
#'   data frame with a warning if no data is returned.
#'
#' @importFrom httr RETRY add_headers stop_for_status content timeout
#' @importFrom dplyr bind_rows
#'
#' @export
pull_daily_rain <- function(
    api_key,
    zipcode = NULL,
    stationid = NULL,
    date_start,
    date_end,
    units = "standard",
    limit = 1000,
    timeout_sec = 10,
    retry_times = 3
) {
    if (is.null(zipcode) && is.null(stationid)) {
        stop("Supply either zipcode or stationid.")
    }

    if (!is.null(stationid)) {
        # one or more stations: repeat stationid= for each, per NOAA's API
        location_params <- paste0("&stationid=", stationid, collapse = "")
    } else {
        zipcode <- as.character(zipcode) # guard against leading-zero loss
        location_params <- paste0("&locationid=ZIP:", zipcode)
    }

    ## ---- url-string

    url_string <- paste0(
        "https://www.ncei.noaa.gov/cdo-web/api/v2/data?",
        "datasetid=GHCND",
        "&datatypeid=PRCP",
        location_params,
        "&startdate=",
        date_start,
        "&enddate=",
        date_end,
        "&units=",
        units,
        "&limit=",
        limit
    )

    ## ---- api-call

    response <- tryCatch(
        httr::RETRY(
            verb = "GET",
            url = url_string,
            httr::add_headers(token = api_key),
            httr::timeout(timeout_sec),
            times = retry_times,
            pause_base = 1,
            pause_cap = 10,
            quiet = TRUE
        ),
        error = function(e) {
            stop(
                "Failed to reach NOAA CDO API after ",
                retry_times,
                " attempts -- ",
                "check your internet connection or try increasing timeout_sec. ",
                "Original error: ",
                conditionMessage(e),
                call. = FALSE
            )
        }
    )

    httr::stop_for_status(response, task = "pull data from NOAA CDO API")

    ## ---- convert-json

    parsed <- httr::content(response, as = "parsed", type = "application/json")

    if (length(parsed$results) == 0) {
        warning("No precipitation data returned for this request.")
        return(data.frame())
    }

    dplyr::bind_rows(lapply(parsed$results, as.data.frame))
}
